## 1. 作る範囲

**デモで通す1本道（これだけは必ず動かす）**（始め方の細部は [設計書（2）](design-d-serial.md)）
1. 作品を始める（物語の軸＋絵柄＋キャラは例から選ぶかパーツ選択＋短い自由記入 → 設定画を確認して確定。作品名は後からでよい）
2. 続きを4行（コマ1〜4のセリフ）で書く → 少し待つと同じキャラの漫画の1ページ（4コマ分）が出る
3. 別の人が同じ所に別の続きを書く → 2本並ぶ
4. 理由を1つ選んで投票 → 多い方が「本筋」になり、その先にまた続きを書ける

**やらない（時間が余っても足さない）**
動画／作者への点・ランキング／コメント欄／ロブロックスのアバターや名前／実在の人の顔／画像アップロード／通知／物語の軸のAI補助／見た目の完全自由記入

**時間が余ったら足す順**
① 書いた人に集まった理由の内訳を見せる画面 ② 画像の保存・共有 ③ キャラ案のAI下書き（余裕枠） ④ 作品名のAI案（後回し）

## 2. 画面（4つ）

| 画面 | 中身 | ログイン |
|---|---|---|
| トップ | 作品一覧・「作品を始める」（連載画面は設計書（2）） | 見るだけなら不要 |
| 作品を始める | 物語の軸・絵柄・キャラ（例またはパーツ＋短文）・作品名任意。詳細は設計書（2）の `/new` | 要 |
| 作品のページ | 本筋の表示・投票・続きを書く。連載形は設計書（2） | 見るだけなら不要 |
| 続きを書く | コマ1〜4のセリフ → 生成中 → 作品のページへ戻る | 要 |

- 投票ボタン: 「続きが気になる」「展開が意外」「キャラが良い」「絵が良い」（話は続くので「オチ」ではなく「引き」を見る）。1人1本につき1票（理由は1つ）。
- **票の数は、自分が投票するまで見せない**（先に入った票に後の票が引っ張られるのを防ぐ。研究の裏付けは「出典」節）。
- 各ページの下に、書いた人の4行をそのまま文字でも出す。絵の中の文字が崩れても、人が書いた言葉が正しく読める。あわせて「話：○○さん　絵：AI」と出す。

## 3. 1ページ（4コマ分）を作る流れ

```
続きの4行 ─▶ ① 文章のAI（Gemini 3.8 Flash）
              ・不適切な内容／実在の人・他作品のキャラの名前がないか確かめる
              ・各コマの「絵の指示」（場面・表情・動き）だけを作る
              ・セリフ欄は持たせない（セリフは人の `lines[4]` だけが正本）
          ─▶ ② 画像のAI（Nano Banana 2.1）を1回呼ぶ
              ・入力: キャラ設定画（1〜2枚）＋ 1つ前のページの画像（あれば）＋ 指示文
              ・指示文にサーバーが `lines[4]` をそのまま埋め込み、「この日本語を一字違わず吹き出しに書け」と渡す
              ・出力: 縦長（2:3）の漫画の1ページ。横長のコマ4つを上から下へ（大事な場面のコマは高くしてよい）
              ・1:4 も実機で使えた（2026-11-10）が 2:3 を使う。横長のコマ4つを縦に積む作りで、スマホで読む幅を保てるため。2:3 でも4コマは崩れなかった
          ─▶ ③ 画像を保存し、続きの状態を「完成」にする → 画面は自動で切り替わる
```

決めた事と理由:
- **4コマ分を1枚で作る**（1コマずつ4回にしない）。料金が4分の1（約5円）、待ちが1回分、1枚の中でキャラがそろいやすい。失敗したら1枚まるごと作り直す。公式の例も「1回で複数コマ」。
- **セリフの正本は人が書いた `lines[4]` だけ**。画面の文字表示もこれ。文章のAIは絵の指示（場面・表情・動き）だけを返し、セリフ欄を持たない。「話は人が書く」を仕組みで守る。絵の中の文字が崩れても、正本は下の人の文。
- **吹き出しの文字も絵に描かせる**。2.1 は日本語が得意な言語に入っており、短い文なら崩れにくいという試し報告がある。崩れても 2 節のとおり下に人の文が出るので、意味は伝わる。指示文には「セリフは日本語で、この文字どおりに」と明記する（「日本語で」と書いても英語になった報告があるため）。
- **キャラは「例から選ぶ」（固定4体）または大きなパーツ選択＋短い自由記入**。[設計書（2）](design-d-serial.md)・[0005](decisions/0005-start-flow.md) が正。設定画は始めた人が確認し、描き直しは1作品2回まで。確定した設定画を毎ページの参照に渡す。実在の人の顔・画像アップロード・見た目の完全自由記入はやらない。
- **1つ前のページも参照に渡す**。話がつながる時に絵柄がずれにくい（前のページを渡す作り方が複数の例で使われている）。

指示文の注意（試した人の報告から）:
- 「絶対に同じ顔」のような強い言い方は逆効果。顔・髪・服・色を具体的に書き、「この4点は変えない」と1文で言う。
- 左右（どちらの手で持つか）は守られにくい。絵の指示に左右を書かない。
- 解像度は 1K（約5円）。スマホで1ページを見るには足りる。

## 4. 使うもの（構成）

| 役割 | 使うもの | 理由 |
|---|---|---|
| 画面とサーバー | Next.js を **Firebase App Hosting** に置く | GitHub につなぐだけで公開まで約5分。画面とサーバーが1つで済む。中身は Cloud Run で動くので大会の条件を満たす |
| ログイン | Firebase Auth（Google ログイン） | 匿名ログインは同じ回線から作れる数に上限があり、会場の Wi-Fi で止まる恐れがある |
| データ | Firestore | 書き換えが画面に即届く（生成中→完成の切り替えに使う） |
| 画像の置き場 | Cloud Storage for Firebase | 1枚1MB前後で、Firestore の1件1MBの上限に入らない |
| 文章のAI | Gemini 3.8 Flash（`gemini-3.8-flash`、2026-11-10 実機確認（global）。[docs/experiments/vertex-smoke.md](experiments/vertex-smoke.md)）を **Vertex AI（Agent Platform）経由**で呼ぶ | 確かめと絵の指示づくり。安くて速い |
| 画像のAI | Nano Banana 2.1（`gemini-nano-banana-2.1`、2026-11-10 実機確認（global）。[docs/experiments/vertex-smoke.md](experiments/vertex-smoke.md)）を **Vertex AI 経由**で呼ぶ | 参照画像でキャラを4人まで保てる。1Kで1枚約0.034ドル |
| 認証 | Cloud Run / App Hosting の**実行サービスアカウント＋ADC** | APIキーは使わない。JSONのサービスアカウント鍵ファイルは作らない・置かない |
| Secret Manager | **現状必須のサーバー秘密は無し**（Vertex は ADC） | 将来サードパーティ鍵が要る時だけ使う。クライアントの Firebase web config は公開前提の識別子（制限付き）なので Secret Manager には置かない |

選ばなかった案:
- Firebase Hosting ＋ Cloud Run を別々に置く：手順が多い（Dockerfile・書き換え設定）。Hosting を通すと1分で切れる（App Hosting は5分）。
- 1コマずつ4回作る：料金4倍・待ちが長い・コマ間でキャラがずれやすい。良い点（失敗したコマだけ直せる）は今回の規模では効かない。
- 吹き出しを空にして文字を後から重ねる：吹き出しの位置が分からないので重ねられない。代わりに下に文字で出す。

## 5. データの形（Firestore）

```
themes/{themeId}        お題
  text          お題の文
  characterIds  選んだキャラ（1〜2）
  authorUid, authorName, createdAt

nodes/{nodeId}          続き（1本＝漫画の1ページ・4コマ分）
  themeId
  parentId      1つ前の続き。お題の直後なら null
  depth         何話目か（1から）
  lines[4]      人が書いた4行（ここが作品の中身）
  panels[4]     文章のAIが作った絵の指示（表示しない）
  status        generating / done / failed / rejected
  deadlineAt    生成の期限（開始 + 120秒）
  failReason    断った・失敗した理由（画面に出す）
  imagePath     Storage の場所
  votes         合計の票数
  reasons       { hiki, igai, chara, e } 理由ごとの票数（hiki＝続きが気になる）
  authorUid, authorName, createdAt

votes/{nodeId}_{uid}    1人1本1票（文書の名前で重複を防ぐ）
  nodeId, uid, reason, createdAt

usage/{uid}_{日付}       1人1日の生成回数
usage/all_{日付}         全体の1日の生成回数
characters/{id}         用意したキャラ（名前・設定の文・設定画の場所）
```

- **本筋の決め方**: 同じ親を持つ**完成した**続きの中で票が一番多い物（同じ数なら先に書かれた物）。生成中・失敗は候補に入れない。候補が無ければ「まだ続きがありません」を出す。毎回、画面で数える。保存はしない（データが少ないので十分速い）。
- **書き込みは全部サーバーから**。画面からは読むだけ。Firestore の規則は「読むのは誰でも・書くのは禁止」。サーバー（Admin SDK）は実行サービスアカウントの ADC で Firestore / Storage / Vertex にアクセスし、規則を通らずに書く。クライアントからの書き込みは規則で禁止。これで「画像の欄を人が書き換える」「票を2回入れる」が起きない。
- 投票はサーバーで1つのまとまった処理（トランザクション）にする: 投票の文書が無ければ作り、票数を1増やす。同じ文書に1秒に何回も書く規模ではないので、票数を分けて数える仕組みは要らない。
- 回数の上限も同じく、生成の前に1つのまとまった処理で「確かめて1増やす」。AIの呼び出しはその外で行う（同時に押されても上限を超えない）。

## 6. サーバーの入口（3つ）

| 入口 | 中身 |
|---|---|
| `POST /api/themes` | お題を作る。文の長さ・キャラの数を確かめ、文章のAIで不適切でないか確かめる |
| `POST /api/nodes` | 続きを作る。①回数の上限を確かめる ②続きを「生成中」で保存 ③ 3節の流れ ④「完成」か「失敗」に更新。全体を **120秒（2分）** で打ち切る |
| `POST /api/votes` | 投票。ログインを確かめ、1人1本1票で記録 |

- どの入口も、ログインの証明（ID トークン）をサーバーで確かめる。
- 打ち切り120秒の根拠: Cloud Run の request timeout は既定5分・最大60分、App Hosting は5分（Hosting は1分）。画像生成を同じ要求の中で待つので50秒では足りない。プラットフォーム上限5分の内側で、待てる長さとして120秒を選ぶ。
- **続きの名前（nodeId）は画面が先に作って送る**。同じ名前が2回届いたら、作り直さずに今の状態を返す（通信が切れて押し直しても二重に作らない・二重に回数を使わない）。
- 「もう一度」は新しい名前で作り直す。完成を書き込む時は「まだ生成中なら」の条件付きにし、期限を過ぎた古い結果が後から上書きしないようにする。
- **期限切れの扱い**: 生成開始時に `deadlineAt = now + 120秒` を保存する。画面は `status==generating` かつ `now > deadlineAt` なら失敗として表示する（読み取りだけで判定）。サーバーは次の書き込み経路（同じお題への `POST /api/nodes` など）で、期限切れの `generating` を `failed` に更新する。完成の書き込みは「まだ generating かつ deadlineAt 前」の条件付き。
- 画像のAIが安全の理由で止めた時（`IMAGE_SAFETY` など）や、画像が返らなかった時は「rejected」か「failed」にし、理由を画面に出す。
- 続きを付ける先は、サーバーで確かめる: 親が在る・同じお題・完成している。

## 7. お金と安全の上限

| 上限 | 値 | 理由 |
|---|---|---|
| 1人1日の生成（ページ） | 10回 | 審査・デモ用に足りる |
| 全体1日の生成 | 120回 | ページ画像＋設定画を同じ枠で数える（1枚＝1回）。約$5.4 ≒ ¥810 で Vertex 支出上限の内側。**月の実効上限は Vertex spend cap でおおよそ140〜150枚**（サービス間で上限は移せない。[0006](decisions/0006-generation-cost.md)） |
| 1人1日の assist | 5回 | Flashのみ・別枠 |
| サーバーの数 | 最大3（`maxInstances: 3`） | チームの決まり（docs/11）。これは同時に生成する数の上限ではないので、生成の数は上の回数で絞る |
| プロジェクト予算（kill switch） | ¥3,000 | docs/11 のとおり |
| Cloud Run 支出上限 | ¥1,000 | docs/11 のとおり |
| Vertex AI 支出上限 | ¥1,000 | docs/11 のとおり |
| Gemini API 支出上限 | ¥1,000 | Developer API は使わない方針なので通常は未使用。使う場合のみ必須 |

**全体1日の上限の再計算**（料金: Model Garden の公式ページ）
- 画像出力 $30 / 1M tokens。1K出力 ≈ 1120 tokens → 約 $0.034 / 枚。
- 入力画像も課金: 1120 tokens × $1.50 / 1M ≈ $0.0017 / 枚。設定画2＋前ページ1で約 $0.005。
- Gemini 3.8 Flash（〜2026-12-31 の導入価格）: 入力 $0.75 / 1M、出力 $3.75 / 1M。1回あたり約 $0.005 と仮定（プロンプト長は未実測の仮定）。
- 1生成あたり合計の保守見積もり: 約 $0.045。
- Vertex 支出上限 ¥1,000 ÷ ¥150/$1（仮定）≒ $6.67 → 生の上限は 6.67 / 0.045 ≈ 148 回。
- 再試行・為替ブレ・テキスト増を見て、全体1日 **120回**（約 $5.4 ≒ ¥810）に設定。
- 旧「20ドルで約500本」は根拠が弱いので外した（要再確認：Issue 予定）。チームクレジット $20 はプロジェクト全体の話で、画像500枚の根拠には使わない。

- 画像のAIは**無料枠が無い**。**最初のデプロイ／最初の Gemini（Vertex）呼び出しより前に**、人が上の予算・支出上限を設定する。カード請求は出さない（大会クレジットの範囲で運用）。11/6 時点では未設定だった。**これが一番先に人がやる事。**
- APIキーは使わず、JSONのサービスアカウント鍵ファイルも作らない。実行サービスアカウントに Vertex / Firestore / Storage の権限を付けて ADC で呼ぶ。提出用のリポは公開なので、移す前に検査を回す（docs/12）。
- 実在の人の写真は受け付けない（画像アップロードはやらない）。
- GCPの予算・spend capは変えない。枚数は設定画抑制・同一入力の使い回し・リトライ上限・1K固定で確保する（[0006](decisions/0006-generation-cost.md)）。

## 8. 作業の分け方（1つ＝1 Issue＝1 PR）

**担当の案**: A＝請求・基盤・生成（0・1・2・3・7）、B＝画面と投票（4・5・6）、C＝通し・デモ・ピッチ（8・9）および 1 の確認手伝い。正確な分割はチームで決める。【チームで】誰がどれを持つか決める。

上から順に。★は1本道に必須。

| 順 | 作業 | 目安 | ★ |

| 3 | 1ページを作るサーバー処理（3節・6節の `/api/nodes`。二重送信と期限切れの扱いを含む） | 2〜3時間 | ★ |

| 5 | お題を出す・続きを書く画面 | 1時間 | ★ |
| 6 | 投票（ボタン・`/api/votes`・自分が投票するまで票数を隠す） | 1時間 | ★ |

| 8 | デモ用のデータを公開先に入れる: 「お題→2本の続き→投票→本筋が変わる→その先の続き」まで | 1時間 | ★ |
| 9 | ピッチの資料・デモ動画（docs/13） | 2時間 | ★ |

- 1 が通るまで他に手を広げない。通らなければ見積もりを引き直す。
- 4・5 は 1 の後すぐ、仮の画像で並行して作れる。
- **11/10 15:00 で機能を止める**。そこから 18:00 までは直す・公開し直す・通しの確認だけ。
- 合格の確かめ方: 公開先で、2つのアカウントで1本道を3回続けて成功させる。加えて「時間切れの後に作り直せる」「送るボタンを2回押しても1本しかできない」を各1回確かめる。

**デモの台本（生成の待ちに頼らない）**
- 最初は 8 で入れておいた作品で「2本→投票→本筋が変わる」を見せる。
- その間に会場のお題で1本生成を始め、話の終わりにできた物を見せる。
- 生成が失敗・遅い時は録画に切り替え、そう言う。

## 9. まだ決まっていない事

- 【チームで】カテゴリー（エンタメかクリエイティブか）、目的と動機（アイデアシート 0・8 節）
