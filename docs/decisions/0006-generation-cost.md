# 0006 生成費用の守り方（上限は据え置き）

- 状態: 決定
- 日付: 2026-11-10（09:55 JST）
- 決定者: @H4aruki。案出しは Miso の調査（`0004-safety-cost.md` の案X・Y・Z、gcloud の読み取り）と Opus の意見
- 関連: #31、PR #63、[0005](0005-start-flow.md)、[0010](0010-gcp-billing-guards.md)、[0012](0012-generation-limits.md)

## 背景

- 絶対条件: **カード請求を出さない**。大会クレジットの範囲で運用する（前提メモ追記 2026-11-04 21:45）。
- 設定済みの上限（#31、gcloud で 2026-11-10 に読み取り確認）:
  - 予算 ¥3,000/月 ×2（通知用と、Pub/Sub の kill switch 用）。どちらもクレジットを除いて計測。
  - spend cap 各 ¥1,000: Vertex AI、Gemini API（Developer API は使わない方針）、Cloud Run、Cloud Run functions。
- クレジット残 **¥3,165**（〜2027-05-05、前提メモ追記 2026-11-10）。spend cap を全部足すと ¥4,000 で、クレジット残を超える。
- サービスごとの上限は**他サービスに移せない**。未使用の Cloud Run の枠を Vertex に足すことはできない。
- 単価（公式 pricing、為替 ¥150/$ 仮定）:
  - Nano Banana 2.1 の 1K 画像出力 ≈ $0.0336/枚、参照画像入力 ≈ $0.0017/枚。
  - Gemini 3.8 Flash ≈ $0.005/回（設計書の仮定、プロンプト長は未実測）。
  - 1ページの保守見積もり ≈ $0.045 ≒ ¥6.8。
- 枚数の上限: Vertex cap ¥1,000 ÷ ¥6.8 ≈ 約148枚/月。アプリの「全体1日120回」より先に**月の cap が効く**。目安は**月140〜150枚**（ページ＋設定画の合計）。
- 開始フロー（[0005](0005-start-flow.md)）で設定画（1作品1〜2枚＋描き直し最大2回）が増える。Opus の試算: 120回 ≈ ¥810 で cap までの余りは約¥190。設定画は約¥5/枚で、20作品×2体なら約¥200 となり、別枠にすると上限超えで当日止まる恐れがある。
- @H4aruki の依頼（2026-11-10）: 今の構成のほかの部分を削って、その分を AI に回せないか検討する。
- Cloud Run・Firestore・Storage はハッカソン規模なら無料枠内の見込みだが、請求ダッシュボードの実額は未取得。

## 検討した選択肢

### 案Z: cap 据え置き＋単価・回数の工夫（採用、Opus も推奨）
- 内容: GCP の予算／spend cap は触らない。同一入力の生成の使い回し（キャッシュ）、失敗リトライの上限、解像度 1K 固定、設定画の枚数を抑える（1体1枚・描き直しは上限まで）、assist と作品名AIは後回し。
- 利点: カード請求のリスクが増えない。設定変更が要らない（コードの生成戦略だけ）。
- 欠点: 月の枚数は約150枚で頭打ち。キャッシュやリトライ制御の実装が要る。

### 案X: 現状維持＋運用で守る
- 内容: 全体1日120・Vertex ¥1,000 のまま、デモ用アカウントと回数を事前に割り当てる。
- 利点: 実装が要らない。
- 欠点: キャッシュなし・設定画ありだと、デモ前に枯渇しやすい。

### 案Y: Cloud Run 等が余っていれば Vertex の cap を上げる
- 利点: 枚数が増える。
- 欠点: 余った cap は他サービスに移せない。Vertex を例えば ¥2,000 にすると、クレジット残との余裕が消え、kill switch（¥3,000）までの他の費用の余地も減る。カード請求のリスクが増える。

### 設定画を回数の完全別枠にする
- 利点: ページ生成の回数が減らない。
- 欠点: 作品あたり1〜2枚で余りを食いやすく、cap を超えやすい。

## 決定

- **GCPの予算・spend capは変えない**。
- 枚数は次で確保する: 設定画の枚数抑制（1体1枚・描き直しは1作品2回まで）／同一入力の使い回し（キャッシュ）／リトライ上限／解像度1K固定。設定画そのものは削らない（[0005](0005-start-flow.md)）。
- アプリの回数上限（1人1日10・全体1日120・設定画も全体枠に1枚＝1回）は設計書どおり。assist は1人1日5回（別枠・Flash）。
- Developer Gemini API は使わない方針のまま（[0002](0002-tech-stack.md)）。

## 理由（判断基準）

1. **カード請求を出さない**（絶対条件）: 案Y は満たさない。案Z・X は満たす。
2. **デモまで枯渇させない**: 案Z は使い回しとリトライ上限で無駄撃ちを減らす。案X は枯渇しやすい。
3. **設定を触らない**: cap を変えると、クレジット残・予算・kill switch の関係を全部見直す必要がある。
4. @H4aruki の決定（2026-11-10）: 費用の上限はそのままにし、生成の工夫で対応する。

## 却下した案と理由

| 案 | 理由 |
|---|---|
| Cloud Run 等の cap を下げて Vertex を上げる | 枠は移せない。Vertex を上げるとクレジット超過・カード請求のリスク |
| 現状維持＋運用だけ（案X） | キャッシュなし・設定画ありでデモ前に枯渇しやすい |
| 設定画を回数の完全別枠にする | 作品あたり1〜2枚で余りを食いやすい（0002-opus／0004） |
| 解像度を上げる | 単価が上がり枚数が減る |

## 影響

- コード: cap 変更なし。生成経路に、同一入力の使い回し（キャッシュ）とリトライ上限を足す。設定画を全体枠で数える。assist の回数を `usage/{uid}_{日付}_assist` で数える。
- 運用: Demo Day までのハード上限は Vertex の月次 cap 側を先に見る。Vertex 生成を試すときは枚数を意識する。
- 費用: Vertex は月 ¥1,000（約140〜150枚）が上限。
- 請求先ID・個人メール・鍵は文書に書かない。

## リスクと対策

| リスク | 対策 |
|---|---|
| Demo Day 前に Vertex の cap に達して生成が止まる | キャッシュ、リトライ上限、設定画の上限。デモは事前に入れた作品で見せ、生成に頼らない（設計書 8節） |
| spend cap は月次でリセットされるので、Demo Day 後も動かすと累計が増える | Demo Day 後の停止を決める（未決） |
| キャッシュの再利用が Google 補償と両立するか | 未改変の再利用なら両立する（Opus の注意） |
| 為替・プロンプト長が仮定と違う | 実額をコンソールで確認する（未実施） |
