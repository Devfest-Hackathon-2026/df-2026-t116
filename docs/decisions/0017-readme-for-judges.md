# 0017 README を審査員向けに作り直す

- 状態: 案（PR #74 の上で @H4aruki が確認する）
- 日付: 2026-11-10 13:00 JST ごろ
- 決定者: 方針は @H4aruki（2026-11-10: README は審査で重要なのでデザインも意識する。14:00 までに PR を出す）。構成と文面は Miso（@H4aruki の AI）が起案
- 関連: Issue #71、[0001](0001-submission-transfer.md)（提出用リポへの移し方）、[0002](0002-tech-stack.md)、[0009](0009-human-story-ai-art.md)

## 背景

- 審査は提出用リポジトリ（公開）の中身だけで行われ、デプロイ URL はその README に書く（前提メモ追記 2026-11-05 10:58）。提出用リポには開発リポの最終版を履歴なしで移す（[0001](0001-submission-transfer.md)）。つまり開発リポの README が、そのまま審査員が最初に読む文書になる。
- 旧 README は開発者向け（hooks の有効化、AI ツールの設定、規約の一覧）で、デプロイ URL は「未定」のままだった。
- 審査はキックオフ資料 p.42 の8項目×0〜3点。README の書式についての大会の指定は、キックオフ資料には無い（"README" で検索して該当なし）。
- 締切: README の PR は 14:00 JST まで（12:15 JST の指示）。コード停止は 18:00 JST、提出は 19:00 JST。

## 検討した選択肢

### 案A: 審査項目の順に節を置き、各節からコードと ADR に飛べるようにする（採用）
- 利点: 審査員が項目ごとに根拠を探さずに済む。主張をコードで確かめられる。
- 欠点: 節が多くなり、README が長くなる。

### 案B: 一般的なテンプレート（概要・機能・インストール・使い方・ライセンス）
- 利点: 見慣れた形。短い。
- 欠点: 審査項目（採用理由、安全性、課題の具体性）との対応が読み手任せになる。

### 案C: 開発者向けの旧 README を残し、審査員向けは別ファイル
- 利点: 開発ルールの説明がそのまま残る。
- 欠点: 審査員が最初に開くのは README。別ファイルは読まれないおそれがある。

## 決定

1. 最初の1画面に、アプリ名・一文の説明・本番 URL・デモ動画（準備中の枠）・チーム、画面3枚を置く（中央寄せ）。
2. 「30秒で分かること」の表で、誰の困りごとか・何をするか・何が新しいか・どう続くか・実行基盤を答える。
3. 試し方（本番）を、2つの Google アカウントで通す7手順で書く。
4. 審査基準の8項目と README の節・根拠ファイルの対応表を置く。
5. 「話は人、絵は AI」を担当の表で示し、仕組みで守っていること（生成の出力にセリフ欄が無い）を書く。
6. 構成図は stack-diagram で作った PNG（`docs/assets/`）。生成の流れは mermaid のシーケンス図。
7. Google 技術は、コードで確かめたものだけをファイル名つきで書く。採用理由は採らなかった案と並べる。
8. 開発者向けの内容（hooks、AI ツールの設定、規約）は README から外し、「開発者向け」節のリンクだけにする。本文は各 doc と AGENTS.md に既にある。
9. #67（設定画の確認）は PR 作成中の 12:20 JST に main へマージされたので、試し方・担当の表・技術の表に入れた。

## 理由（判断基準）

- 審査項目に直接答えること（案A）。
- 主張を確かめられること: 「審査員は README を信じない」前提で、主張ごとにコードか ADR を示す（X 上の投稿の調査）。
- 冒頭で「何の問題を解くか」「試し方」「デモ動画」が分かること（X 上の投稿の調査）。
- 機械にも読みやすいこと: 審査の一部を AI がする大会が出てきている。表と見出し中心にし、画像には説明の alt を付ける（X 上の投稿の調査）。
- 事実を作らないこと: 数字は apphosting.yaml・コード・ADR にあるものだけ。spend cap の金額や予算額は README に書かない（公開リポで必要がない）。

## 却下した案と理由

| 案 | 採らなかった理由 |
|---|---|
| shields.io などのバッジを並べる | 外部の画像サーバーに依存する。審査項目に効く情報が無い。技術は表で示す |
| 絵文字の見出し・装飾 | AI っぽく見える（@H4aruki の関心）。GitHub の Alerts も1〜2個に抑える（GitHub Docs） |
| 動く図（JS で動くアーキテクチャ図） | GitHub の README では JS が動かない |
| 仮の画像（それらしく作った画面や絵） | 偽装と取られるおそれ（キックオフ p.46「デモ動画の偽装」は対象外）。撮れない画像は差し替え場所を HTML コメントで示す |
| 本番画面のスクリーンショット | 12:30 JST 時点で本番に作品が0件（`/api/themes` が空）で、空の画面しか撮れない。生成を走らせると課金されるので撮影のために作らない |

## 影響

- コード: なし（README.md、docs/assets/、この ADR、docs/MAP.md の1行）。
- 運用: 提出用リポへ移すとき（[0001](0001-submission-transfer.md)）、README はそのまま移す。リンク先の docs/ も一緒に移る前提。
- 画像: 画面は #61 で撮った開発用の生成器の画面（`docs/screenshots/59/`）を流用し、そう明記した。本番の絵が撮れたら差し替える。
