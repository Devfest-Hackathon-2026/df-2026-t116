# 0013 チーム共有は GitHub 基本（秘密だけ Discord）

- 状態: 決定
- 日付: 2026-11-10（共有ルール 06:05 JST、文書の事前確認 06:27 JST ごろ、PR 上での確認の例外は同日午前）
- 決定者: Haruki さん
- 関連: [0014](0014-dev-workflow.md)、[docs/12](../12-secrets.md)

## 背景

- 口頭や Discord だけだと決定が残らず、後から追えない。PR レビューや検索とも結びつかない。
- 一方、鍵・トークン・個人情報は GitHub に置けない（提出用の公開リポジトリへ混入するおそれ、[0001](0001-submission-transfer.md)）。
- 2026-11-09 08:58 に、Discord 投稿をボイスチャンネル「一般」付属のチャット（名前が同じ別チャンネル）に送ってしまう取り違えがあった。
- AI が書いた文書や投稿文が、Haruki さんの意図とずれたまま出ることがあった（06:27 以降、文書の文章は Haruki さんに見せてからにする運用）。
- メンバーは主に Claude Code と Codex を使う。Grok Bot にしかできない作業はメンバーにはできない。

## 検討した選択肢

### 案A: GitHub 基本、秘密だけ Discord のテキストチャンネル、投稿前に Haruki さんが確認（採用）
- 利点: 決定と経緯が Issue / PR / docs に残り、PR レビューで確かめられる。秘密は GitHub に入らない。
- 欠点: 投稿までに Haruki さんの確認待ちが入る。

### 案B: すべて Discord
- 利点: 速い。
- 欠点: 検索性・履歴・PR レビューとのつながりが弱い。

### 案C: 秘密も GitHub の非公開リポジトリに置く
- 利点: 1か所にまとまる。
- 欠点: 提出用の公開リポジトリへの混入と漏洩のリスク。

## 決定

- チームへの共有は **基本 GitHub**（Issue / PR / docs）。
- **セキュリティ上 GitHub に上げられないものだけ Discord**。
- Discord は **テキストチャンネル**に投稿する（ボイスのチャット欄にしない）。投稿前にチャンネルの種類を確認する（Discord API でテキストは type 0、ボイスは type 2）。
- Discord 投稿の前に **Haruki さんの確認**を取る。全文を見せ、「投稿して」と言われてから投稿する。
- ドキュメント・PR 本文・Issue 本文の文案も、投稿・push 前に Haruki さんへ見せる。例外: 設計書などの PR は、PR を出して Haruki さんが PR 上で確認する（Haruki さん「PR出してもらえればPR上で確認する」）。
- メンバー向けの文は人が読める形にする。理由を短く添える。Grok Bot にしかできない作業は Haruki さんの担当として書き、メンバーに必要なログインがあれば書く。

## 理由（判断基準）

1. **残る・追える**: GitHub なら決定の経緯とレビューが残る（案B は弱い）。
2. **秘密を守る**: 秘密は GitHub に入れない（案C は危険）。
3. **取り違えを防ぐ**: テキストチャンネルの種類を確認する（11/9 の事故）。
4. **意図とのずれを防ぐ**: 外に出る文は Haruki さんが先に見る。PR は PR 上で見られるので例外にする。

## 却下した案と理由

| 案 | 理由 |
|---|---|
| すべて Discord | 検索性・履歴・PR レビューとのつながりが弱い |
| 秘密も GitHub の private に | 提出用公開リポへの混入・漏洩リスク |
| ボイスチャンネル付属のチャットに投稿 | 名前が同じで取り違えやすく、テキストチャンネルと別物 |

## 影響

- 運用: ボットは Discord 投稿前に文案を提示する。鍵・トークン・請求先IDはチャットにも貼らない。
- 運用: 決定は ADR と PR 本文に残す（[0014](0014-dev-workflow.md)、AGENTS.md）。
- コード・費用: なし。

## リスクと対策

| リスク | 対策 |
|---|---|
| 確認待ちで共有が遅れる | PR は PR 上での確認でよい。急ぎのときは短い要約を先に見せる |
| Discord に秘密を貼ったまま残る | 貼る前に Haruki さんが確認。不要になったら消す |
