# 0001 提出用リポジトリへの移し方

- 状態: 決定
- 日付: 2026-11-05（開発用リポジトリ作成時のコミット e49e0cd、13:14 JST）
- 決定者: 前提（運営ルールと Haruki さんの確認、前提メモ追記 2026-11-05 10:58）に沿って AI が手順を起案。手順そのものへの Haruki さんの明示承認は未確認（main に入っているのは作成時の直接コミット）
- 関連: #49（移す前の秘密検査）、#50（提出の人作業）、[0003](0003-org-and-visibility.md)

## 背景

- 提出用リポジトリ <https://github.com/Devfest-Hackathon-2026/df-2026-t116> は運営が用意した**公開**リポジトリ。審査はこのリポジトリの中身だけで行われる。GitHub Actions と Pages は使えない（前提メモ追記 2026-11-05 10:58）。
- 開発はここでせず、別の開発用リポジトリ（非公開、[0003](0003-org-and-visibility.md)）で行う。**開発リポジトリの履歴ごと push しない**ことが前提メモに明記されている。
- 秘密情報は絶対にコミットしない。誤公開時は即削除・無効化、高額請求は運営免責（前提メモ追記 2026-11-09 15:06）。
- 期限: コード締切 11/10 18:00 JST（実務上の停止）、凍結 19:00 JST（以降は push しない）。提出締切後は Regional Day 終了まで読み取り専用（キックオフ資料 p33）。
- README にデプロイ URL を書く。デプロイ URL は 11/14 まで動かしておく（キックオフ資料 p40・p49）。LICENSE は MIT（変更可）。

## 検討した選択肢

### 案A: `git archive` で最終版だけを書き出し、1コミットにして push（採用）
- 利点: 履歴が一切出ない。手順が短く、誰でも同じ結果になる。書き出したディレクトリを gitleaks で丸ごと検査できる。
- 欠点: 提出側に開発の経緯が残らない（審査で履歴は使われない前提）。`git archive` は追跡中のファイルしか出さないため、追跡外の必要ファイルがあれば漏れる。

### 案B: 開発用リポジトリをそのまま提出先へ push
- 利点: 一番手早い。
- 欠点: 開発中の全履歴（途中の試行、消した設定、万一の秘密情報の痕跡）が公開される。前提メモの「履歴ごと push しない」に反する。

### 案C: `git filter-repo` で履歴を書き換えてから push
- 利点: 履歴の一部を残せる。
- 欠点: 手間がかかり、消し漏れが出うる。締切直前の作業として重い。

### 案D: 開発用リポジトリを公開に切り替える
- 利点: 移す作業が要らない。
- 欠点: 提出先は運営の別リポジトリなので使えない。

## 決定

main の最終コミットから `git archive` で書き出し、新しい空ディレクトリで `git init` して単一コミットを作り、df-2026-t116 の main に push する。

```sh
# 開発リポジトリで、最終コミットを確認してから実行
OUT=$(mktemp -d)
git archive --format=tar main | tar -x -C "$OUT"

cd "$OUT"
gitleaks dir .            # 古い版: gitleaks detect --no-git --source .
git init -b main
git add .
git commit -m "chore: 提出版"
git remote add origin https://github.com/Devfest-Hackathon-2026/df-2026-t116.git
git push origin main
```

### push 前チェック

- README にデプロイ URL がある。
- LICENSE が MIT。
- `.env` などの秘密情報が含まれない。
- 書き出したディレクトリで `gitleaks dir .`（または `gitleaks detect --no-git`）を実行し、検出ゼロ。

## 理由（判断基準）

1. **安全**: 公開リポジトリに出るのは最終版のファイルだけにする。履歴に残った秘密情報の痕跡を構造的に出さない（案Aだけが満たす）。
2. **確実さ**: 締切直前でも手順が短く失敗しにくい（案A > 案C）。
3. **ルール適合**: 「履歴ごと push しない」「秘密情報をコミットしない」（案B は不適合）。

## 却下した案と理由

| 案 | 採らなかった理由 |
|---|---|
| 開発リポジトリをそのまま push | 開発中の履歴がすべて公開される。前提メモに反する |
| `git filter-repo` で履歴を消す | 手間がかかり、取りこぼしが出うる |
| 開発リポジトリを公開に切り替える | 提出先が別リポジトリなので使えない |

## 影響

- コード: なし（手順のみ）。
- 運用: 提出リポジトリの履歴は 1 コミットだけになる。凍結（19:00）後の修正は提出に反映しない。push する人は提出リポジトリに書き込み権限のある人（Haruki さんは権限あり）。
- 費用: なし。
